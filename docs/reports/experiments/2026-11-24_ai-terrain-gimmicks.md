# 戦闘中に装置を使うAIの実験

敵が二つのスイッチの間にいるとき、AIは操作できる側から、そのtickで選んだ敵に効果が届く方を選ぶ。押す直前に味方が入れば手を止める。この一連の判断を敵の `AIInfo`、中央tick、Burst Job、実際のシーンイベントまでつないだ。

## Unityで確かめた場面

| 場面 | 結果 |
|---|---|
| シスターがプレイヤーの退避を待つ | 実際の `CompanionCharacter` で、プレイヤーだけが範囲内、敵も進入、プレイヤー退出、次の判断と4回進めた。同じ敵を狙い続け、累積起動回数は **0 → 0 → 1 → 1**。操作を待つ2回はガードした。 |
| 同じtickに標的を変更 | 新しい標的に対応するスイッチが1回作動し、扉のColliderが無効になった。旧標的側のスイッチは使える状態で残った。 |
| 使える装置と使えない装置が混在 | 味方を巻き込む候補、種類違い、旧標的側を除いた。等距離の安全な候補を逆順に登録しても、同期判定と一括Jobが同じ登録IDを選んだ。 |
| 敵が遅延効果の範囲へ走り込む | 敵の現在速度で効果時の位置を予測して起動した。選択後に味方が加速して横切るケースでは起動を見送り、ガードに戻った。 |
| 手前のスイッチとの間に壁がある | 観測時に閉じていれば奥の操作可能なスイッチを選んだ。選んだ後に壁が閉じた場合はどちらも押さず、ガードに戻った。 |
| スイッチを押す直前に攻撃を受ける | 被弾硬直を検出して操作を中止し、スイッチは次に使える状態で残った。 |
| 2体が同じ敵に対して同じスイッチを選ぶ | 起動イベントは1回だけ発生した。操作できなかった側はそのtickでガードし、次のtickには両者ともガードした。 |
| 装置や戦況が選択後に変化 | 操作者自身が範囲に入った場合や、装置が無効化・再有効化された場合に古い要求を拒否した。再観測後は新しい世代を使用できた。 |
| 部屋を移動する。同じtickに別の扉が動く | 管理オブジェクトを維持して元の部屋を破棄しても、移動先で操作できた。別の物理ワールドの同一座標にいる味方は候補に影響しなかった。選択後に扉が操作線上に移動すれば、次の物理ステップを待たずに操作を中止した。 |

LinuxのUnity 6000.6.8f1で、物理だけを切り分けたシーンも0.02秒刻みで実行した。接触板を横切る経路は最初の接触が0.64秒、接触37ステップで起動1回、隣の経路は接触0回だった。二つの範囲物の片方にしか味方がいない配置から味方を移すと、起動時の照会は両方への巻き込みを検出した。落下物の初接触は予測0.714秒に対し実測0.720秒で、その場から離れる相手への接触は0回だった。

移動の対照実験には連続床、3mの溝、橋を使った。同じ歩行入力で連続床と橋は対岸に達し、溝では落下した。溝に踏切を与えた場合は x = −1.96 から跳んで x = 3.74 に着地した。この実験で制御したのは歩行入力と踏切で、自律的な迂回経路の探索は引き続き計画にある。

## シスターが何に気づき、いつ行動を変えたか

優先4場面は、1秒刻みで0秒から6秒まで進むモデルで17ケースを実行した。うち14組は世界の条件を一つだけ変えた対照で、観測の変化、方針を見直した理由、実際に始めた行動とその相手・地点を別々に照合した。時刻はこの実験の設定値である。

| 場面 | 観測から行動までの記録 | 判断に必要だったデータ |
|---|---|---|
| 溝の向こうへ逃げた敵を追う途中で、別の敵がプレイヤーに詠唱 | 1秒に予告を見ればその場で引き返した。2秒に離陸し3秒で予告を見た場合は、その時点で護衛に切り替えると決め、4秒の着地後に帰路を開始した。 | 追撃相手・護衛相手・詠唱者とその標的、移動の段階、次に行動を変えられる時点 |
| プレイヤーが盾持ちを引きつける | 正面を抑え続けると3秒で側面へ到達。プレイヤーが近くにいても、2秒に敵がこちらを向くか、プレイヤーが離脱すると、その時点で援護へ切り替えた。 | 誰が誰と交戦中か、盾の向き、選択済みの経路 |
| 敵を罠へ誘う | 2秒に敵が入り、3秒にプレイヤーが出たら起動した。敵が来ない場合も、味方が出ない場合も、5秒で諦めて護衛へ戻った。 | 使う装置と誘う敵、範囲を出入りした個体、待機の期限、一度起動した事実 |
| 見失った敵を探す | 1秒に見失い、2秒に最後の目撃地点、3秒に左の足音を確認。隠れた敵が左右どちらにいても全記録が一致した。4秒に姿が見えた場合にだけ再照準し、見えないままなら5秒で護衛へ戻った。 | 観測者、情報源、最後に見た場所と時刻、調べる地点、照準を向けてよい個体 |

1体の戦闘標的だけでは「逃げた敵を覚えたまま、詠唱者からプレイヤーを守る」関係を復元できない。護衛対象や継続中の目的は次のtickに保持し、距離や到達時間はその時点の観測から求められる。足音は調べる地点を渡せても、遮蔽の裏の個体を照準対象にする根拠にはならない。これらの関係と中断条件を機能DBの `terrain-aware-action-selection` に記録した。

|---|---:|---|

| 経路 | 18,432 | 操作点、効果地点、片方向リンク、跳躍能力、着地の空き、橋と受付期限 |
| 受付から発動まで | 11,904 | 二者の実行順、要求の再送、物体や標的の入れ替わり、再使用待ち |
| 知覚と役割 | 2,448 | 死角、未観測と空、追撃・護衛・回避、標的切替、同種の装置 |
| 連動装置 | 2,700 | スイッチの分岐・合流・循環、遅れて変化する足場と危険区画 |
| 行動の時間 | 864 + 別条件864 | 現在の行動が終わる時刻、移動、予備動作、遅延、敵味方の滞在時間 |

各モデルで入力を1群ずつ隠し、残りが同じでも期待結果が分かれるか調べた。67,452条件の53群中52群で反例が見つかった。残る1群は処理済みの要求・効果の再送で、二重発動を防ぐモデルでは結果が一致した。集計は列挙した条件を等しく扱う。ゲーム内での発生率は測っていない。

時間判定の864条件では、観測直後に使えると仮定すると284件誤った。移動・予備動作・効果遅延を入れると112件、現在の行動の硬直時間も入れると0件になった。異なる時間値を使った追加864条件では、同じ順に93件、125件、0件だった。途中段階では条件を増やしただけで成績が悪化している。連動装置でも、最初の接続先だけを見ると2,700条件のうち不要な起動270件と使い逃し130件が生じた。

本体が扱うのは操作圏・固体遮蔽・標的の世代と陣営・効果範囲・起動から効果までの遅延・現在の行動制限。遅延中の移動は等速と仮定する。長い迂回の所要時間、罠への誘導、連鎖先の効果、装置ごとの再使用待ちはモデルの検証結果を次の計画に引き継ぐ。

## 敵の集団と、空いている床を狙う場合

2Dの地点指定技をモデルにし、床・個体・当たり部位の列挙順をそれぞれ逆にして、12場面を8通りずつ実行した。選んだ床、予測した敵の世代付きID、発射の可否、着弾時に範囲にいた敵と味方は、96通りすべてで事前に記述した期待値と一致した。同じ座標にある二つの部位を「敵2体」から「ボス1体」に変えただけで、狙うべき床が変わった。

発射を選んだ80通りのうち24通りで、着弾時の対象が選択時の予測と違った。原因は発射**後**の味方の進入、敵の離脱、同じIDを使う別世代への交代である。味方が発射**前**に入れば見送れた。判断記録には観測した候補集合、実行命令には選んだ地点・向き、効果の記録には実際に当たった個体が必要になる。この照合にはPython側で独立に計算した着弾判定を使った。

## 添付の例から追加した対照実験

### スタン中の敵へ初撃が間に合うか

近くの通常敵Aと、スタン中の敵Bがいる11場面で、どちらを狙うかを試した。「Bが5m以内で、初撃がスタン解除より先ならB」をこの実験の期待値とした。距離上限ちょうどの5mを含め、解除と同時の初撃は機会を逃した扱いにした。現在の行動の硬直200ms、攻撃が届くまでの移動1,000ms、予備動作100msなら、Bのスタン残り1,301msでB、1,300msでAとなる。

距離だけで選ぶと手書きの期待値と4件違い、候補のスタン効果の有無と距離で選ぶと5件違った。残り時間と初撃までの所要時間を照合して全11件が一致した。一条件ずつ変えた9組のうち5組では、モデルで固定した位置・行動状態などの観測値が同じでも選ぶ相手が変わった。スタン残り時間は既に状態効果ストアにある。レビュー後の実装はこの値を同じtickの観測へ渡し、設定した秒数を超える候補を選ぶ。技ごとの移動と発生の見積もりは次段階に残る。[状態効果ストア](../../../Assets/MyAsset/Core/Damage/StatusEffectStore.cs)・[標的と条件の判定](../../../Assets/MyAsset/Core/AI/Core/AIQueryKernel.cs)

本体のコンパイル済みDLLでも、4秒のスタンを付与し、3.5秒進めて比較した。残りは4秒から0.5秒へ変わったが、両時点ともスタン有効、行動不可、有効効果数1だった。同じ状態フラグを見ても残り時間は復元できない。証跡ZIPの `game-core-probe/` に、この照合と次の標的交換を再現するC#ソース・実行スクリプト・出力を同梱した。

### 二人の味方を狙う敵と、妨害を引き取る時点

このプロジェクトがビルドした `Game.Core.dll` で、敵11・12の標的を「11→21、12→22」から「11→22、12→21」へ交換した。正本の `TryGetTarget` は交換を返したが、共通観測の人数と `TargetingCount` のソート値はどちらも両方のtickで (1, 1) だった。味方21を守るために止めるべき敵は11から12へ変わる。改善前の共通観測は標的関係を人数に集約していた。レビュー後は同じ人数でも、候補ごとの標的を読み分けられる。[標的関係の正本](../../../Assets/MyAsset/Core/AI/Core/AITargetRelations.cs)・[共通観測](../../../Assets/MyAsset/Core/AI/Core/AIObservationContext.cs)

その先の連携を、護衛対象1人・妨害を頼める味方1人・詠唱者2人のモデルで20場面、敵の列挙順を反転して40回再生した。手書きの54判断と一致した。依頼しただけなら自分で止めに入り、味方が受理して締切に間に合うなら待った。味方の空振りが確認できた場合も、自分の準備が間に合えば妨害を引き取り、1tick遅ければ護衛対象をガードする。古い行動のキャンセル通知を再送しても、新しい担当は消えなかった。

本体の `HitConfirmed` は、技に紐づく正のダメージが入り、ガードが成立しなかった場合に出る。通知が届かない理由には、ガードや遅延効果の着弾待ちもある。モデルでは「技終了・結果待ち」「空振りを確認」「期限を過ぎて結果不明」を分けた。ここで増やした実験は判断に必要なデータの検証で、担当の受理・命中結果を共有するAIの接続は計画に残る。[命中確認の発行条件](../../../Assets/MyAsset/Runtime/Combat/GameActionRuntime.cs)

## データフローのレビューと改善

判断を作る時点と実行する時点を分けて、同じ入力がどこまで届くかを調べた。

| 見つけた問題 | 実装で変更したこと | 回帰テストで区別する場面 |
|---|---|---|
| 標的の正本にある「誰が誰を狙うか」が、共通観測で人数に変わる。スタンも状態フラグから残り時間を復元できない。 | 固定tickで個体の世代を確かめ、標的・被ターゲット数・プレイヤー・スタン残り秒数を観測に保存。優先ルールが使う場合はBurstへも対象ごとに一度コピーする。 | 同数のまま狙い先が入れ替わる、残り時間が閾値ちょうど、未取得と既知の0、観測後に状態効果を解除する。 |
| 設定画面と実行側に別々の弱点属性欄があり、旧欄だけの指定が選択結果に届かなかった。公開されている同期版とJobで候補の選定ループも重複していた。 | 弱点設定に一つの読み口を設けた。明示された現在の設定を優先し、旧欄だけの場合は指定属性のいずれかを採用する。画面・同期・Burstは同じ解釈を使う。 | 火と雷について「両方」と「どちらか」で異なる候補を選ぶ。既存の戦術設定を編集・保存しても優先条件が残る。 |
| 行動にクールタイム完了や標的の状態効果を指定しても、作者データの変換時に未対応の条件が消え、攻撃や装置操作が無条件で選ばれ得た。 | 変換できない条件を指定した行動は、スロット番号を保って自動選択と既定行動から外す。対応する行動が一つもなければ何も選ばない。 | 未対応条件を持つガード・攻撃だけのモードと、実行できる待機・攻撃・装置操作が一つ加わったモードを比較した。 |
| Jobの結果を待つ間に実行者の標的が変更されても、旧標的が生存していれば古い判断が変更を巻き戻せた。 | 判断開始時の標的を世代付きで保持し、反映直前の関係が変わっていれば破棄する。通常の判断で新しい標的を選ぶ場合は従来どおり反映する。 | 待機中の標的変更・解除、同じハッシュの別世代、装置の起動拒否に伴うコールバックが新しい標的を設定する。 |
| 接近や追従で、観測が使える場合も物理やSoAの座標を先読みしていた。片方だけ観測できた場合には移動方向に異なる時点の座標が混じった。 | 操作者と標的の座標を対で読み、両者の観測がそろわないときに初めて元の座標取得経路を使う。 | 観測済みの2者、片方だけが観測済みの2者、別々の物理ワールドにいる2者。 |

データの流れは、キャラクターと状態効果の更新 → そのtickの観測確定 → 同期またはBurstの共通選定 → 標的の世代・変更の照合 → 行動実行、の順になる。操作直前の巻き込みや閉じた扉は実行時の物理状態で再確認する。護衛のテストは実際の `CompanionCharacter` と作者用 `AIInfo` からこの一連の経路を通る。[観測の収集](../../../Assets/MyAsset/Core/AI/Core/AIObservationCoordinator.cs)・[共通選定](../../../Assets/MyAsset/Core/AI/Core/AIQueryKernel.cs)・[結果の適用](../../../Assets/MyAsset/Core/AI/Core/AIDecisionSystem.cs)・[シーン内の回帰テスト](../../../Assets/Tests/PlayMode/AIObservationFlowTests.cs)

護衛のシスターに「スタンがあと1秒を超えて続く、プレイヤーを狙う敵を優先」と設定した。2.5秒のスタンを与えて0.6秒進めると、近くの通常敵を越えて、遠くの攻撃者を選んだ。そこでスタンを解除しても、この判断が読んだ残り時間は1.9秒のままだった。次の観測で初めて残り0秒を読み、攻撃者がプレイヤーを狙い続けていても近くの敵に切り替わった。

既存の距離選択ベンチマークでも、100体が100候補から選ぶ処理を照合した。Editor上で10回を1組として20組測った。1組の計測時間を10で割ると、1判断tickあたりの中央値は同期で0.987msから0.512ms、Burst一括で0.539msから0.443msになった。前版で1回分として掲載した5.12msと4.43msは、レビュー後の10回分の合計だった。護衛・スタンの追加条件は無効。実験アーカイブの `unity/benchmark-100-actors.json` に測定値と換算値を収録した。[ベンチマーク条件](../../../Assets/Tests/EditMode/Performance_BaselineBenchmarks.cs)

残る設計上の境界は、候補ごとの初撃時刻と、味方に任せた攻撃の結果である。前者には技の発生と実際の経路が要り、後者には担当の受理・行動ID・着弾待ち・確定した効果が要る。どちらも上のモデルの検証条件を残した。

## 読むデータと候補順を変えた同期・Burst比較

100体のAIが、味方のプレイヤー1体と敵100体のいる同じ配置で判断する。同期とBurstのそれぞれに、別々に初期化した同じ世界を渡した。候補の順番は全員が登録順に読む場合と、同じ固定シードで並べ替えたリストを読む場合を比較した。並べ替えは計測前に1回だけ行い、順番を変えても正解が一意になるように配置した。[計測コードと各AIの期待値](../../../Assets/Tests/EditMode/Performance_AIObservationWorkloads.cs)

| 判断 | 全100体で照合した結果 |
|---|---|
| 距離 | 各AIが自分に一番近い敵を選んで攻撃を要求する。 |
| プレイヤー護衛とスタン | 敵50体がプレイヤーを狙い、別条件で50体に2秒のスタンが残る。両方を満たす25体から最も近い敵を選ぶ。状態効果ストアは全ケースで接続し、各判断の開始時に読み直す。 |
| 被ダメージ履歴 | 各AIに4体の異なる敵からのダメージを記録し、自分に最大のダメージを与えた敵を選ぶ。1,000候補のケースでも記録は1人4件で、観測する個体は201体から1,101体へ増える。 |
| 装置と味方の安全 | 10基のスイッチの操作範囲と効果範囲、標的、味方の位置を照合する。45体は対応するスイッチの操作を要求し、5体はプレイヤーを巻き込むため通常攻撃を選び、50体は標的が効果範囲外で通常攻撃を選ぶ。 |

時間には観測の作り直し、全員の判断、コマンドの記録までを含む。Burstには候補のコピーとインデックス変換、ジョブのスケジュール、完了待ち、結果の適用も含む。スタン時間と装置は、毎回同じ場面を比較できるよう固定した。実際の物理照会や装置の作動、攻撃演出は計測範囲外である。[一括処理](../../../Assets/MyAsset/Core/AI/Core/AIDecisionSystem.cs)

```sh
    --non-interactive -- --burst-force-sync-compilation || break
done
```

### 状況が続くときの判断方針

次の対照場面は、1回の観測から計算できる量と、前の判断から引き継ぐ情報を見分けるために使う。期限はゲーム内時間で比較する。

| 対照場面 | 記録する情報と、判断を切り替える条件 |
|---|---|
| プレイヤーが同じ方向に回避した後で癖を変える。ボスが本攻撃とフェイントを混ぜる。 | 回避は直近の観測回数・方向と信頼度、予備動作は解放の合図と実際の結果を対応づける。反例で信頼度を下げ、古い傾向は失効させる。 |
| 移動する目標への二経路がほぼ同点。狭い入口に2回失敗した後で開通する。 | 同点付近では前回経路を保つ。閉塞したら切り替え、同じ入口への再試行は失敗理由・時刻で抑える。開通の観測で待機を解除する。 |
| 味方が大技を準備中。味方の攻撃が外れる。罠の近くを味方が横切る。 | 攻撃予定の範囲と時刻を読んで敵を留め、自分は退避する。命中確認か攻撃終了を待って追撃を決める。罠は敵が入り味方が出るまで待ち、期限で誘導を打ち切る。 |
| 2人の味方が別々に狙われる。自分が弾を避けると背後の護衛対象に当たる。 | 自分が守る味方と、妨害を依頼する味方・敵を明示する。依頼の受理と到着期限を照合し、回避後の弾道まで含めて盾・割り込みを選ぶ。 |
| 負傷した護衛対象の近くで足音。角には左向きの足跡があるが敵は右にいるかもしれない。味方と狭い通路で鉢合わせる。 | 最終目撃と推測を分け、確認できるまで照準を確定しない。探索距離・時間に上限を設け護衛へ戻る。通路は先行者の退出か譲る期限で再評価する。 |
